Plano de migração do modelo de cache atual (sem `cacheComponents`) para o [Cache Components](https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents) do Next 16, para que as leituras feitas pela camada de [service](/docs/banco-de-dados) fiquem cacheadas com tempo de vida explícito e as mutações invalidem exatamente o que mudou.

Decisões confirmadas:

- Migração conduzida manualmente, fase por fase, sem instalar o skill oficial da Vercel (`next-cache-components-adoption`).
- Para tudo que envolve permissões/membros/papéis/planos/empresa ativa: sempre `updateTag` (invalidação imediata, read-your-own-writes), nunca `revalidateTag` (stale-while-revalidate) — correção acima de performance de cache.

## Inventário (levantado antes de iniciar)

- Nenhuma página/layout chama Prisma diretamente; tudo passa por `lib/services/*.service.ts` (`empresaService`, `roleService`, `planoService`, `userService`, `agendamentoService`). Cliente Prisma: `lib/db.ts`, exportado como `db`.
- Único uso de `cookies()`/`headers()` em caminho de renderização: `getAccessContext()` em `lib/access-control/context.ts` (lê cookie `empresa_ativa_id`, faz `db.user.findUnique` com memberships, e chama `planoService.buscarMatriz`, hoje `React.cache()`).
- `getAccessContext()`/`auth()` são chamados sem `<Suspense>` no topo de ~11 layouts/pages: `app/dashboard/layout.tsx`, `app/dashboard/empresa/layout.tsx`, `app/agenda/layout.tsx`, `app/(admin)/admin/layout.tsx`, `app/dashboard/docs/layout.tsx`, `app/dashboard/emails/layout.tsx`, `components/sidebar/layout.tsx`, e as pages `app/dashboard/page.tsx`, `app/dashboard/empresa/page.tsx`, `app/dashboard/empresa/membros/page.tsx`, `app/dashboard/empresa/papeis/page.tsx`, `app/dashboard/exemplos/page.tsx`, `app/(admin)/admin/planos/page.tsx`, além de `app/(auth)/*` e `app/page.tsx` com `auth()`.
- Server Actions com `revalidatePath` que vão ganhar `updateTag` complementar: `app/dashboard/_components/actions.ts`, `app/dashboard/empresa/membros/_components/actions.ts` (×5), `app/dashboard/empresa/papeis/_components/actions.ts` (×4), `app/agenda/_components/engine/agendamento.actions.ts`, `app/(admin)/admin/planos/_components/actions.ts` (×2), `components/sidebar/actions.ts`.
- Nenhum `export const dynamic/revalidate/fetchCache` hoje.
- Serviços retornam `DataBaseResponse` ([ver banco de dados](/docs/banco-de-dados)) em vez de dado cru — a compatibilidade desse wrapper com a serialização exigida por `"use cache"` precisa ser verificada no início da Fase 1.

## Fase 0 — Habilitar a flag e estabilizar o build

- [x] Adicionar `cacheComponents: true` em `next.config.ts`.
- [x] Rodar `npx @next/codemod@canary cache-components-instant-false ./app` (opt-out mecânico de todas as rotas via `export const instant = false`, 32 arquivos).
- [x] `tsc --noEmit` + `next dev` para confirmar ausência de erros de IO síncrono. Encontrado um caso real: `app/page.tsx` chamava `auth()` (que faz `crypto.getRandomValues()` internamente ao decodificar a sessão) no topo da página, bloqueando o prerender mesmo com `instant = false` (esse erro não é suprimido pelo opt-out). Corrigido movendo a leitura de sessão para um componente `AccountNavActions` dentro de `<Suspense fallback={<GuestNavActions />}>`, removendo o `instant = false` dessa rota — ela já está migrada.
- [x] Commit isolado, sem mudança de comportamento visível (pendente de commit pelo usuário).

## Fase 1 — Cachear a camada de serviço

- [x] Confirmado: `DataBaseResponse` é instância de classe (`DataBaseSuccess`/`DataBaseError` dentro), não serializável como retorno de `"use cache"`. Solução adotada: a query Prisma crua vira uma função `"use cache"` module-level (não exportada), e o método público do service continua chamando `DataBaseResponse.fromPromise(() => funcaoCached(...))` — a API pública do service não muda.
- [x] Tags centralizadas em `lib/services/config/cache-tags.ts` (uma função por entidade: `empresaTag`, `membrosTag`, `convitesTag`, `empresasDoUsuarioTag`, `planoMatrizTag`, `eventosAgendaTag`) — evita divergência entre a tag usada na leitura (`cacheTag`) e na invalidação (`updateTag`).
- [x] `empresa.service.ts`: cacheadas `buscarPorId` (`cacheLife('hours')`), `listarDoUsuario`, `listarMembros`, `listarConvitesPendentes` (`cacheLife('minutes')`). `updateTag` adicionado em `criarEmpresa`, `atualizarConfiguracao`, `alterarPapelMembro`, `inativarMembro`, `criarConviteEEnviar`, `revogarConvite`, `aceitarConvite`.
- [x] `plano.service.ts`: `buscarMatriz` convertido de `React.cache()` (memoização por request) para `"use cache"` + `cacheTag('plano-matriz:...')`, `cacheLife('hours')` — agora persiste entre requests, não só dentro de um. `updateTag` em `salvarMatriz`.
- [x] `agendamento.service.ts`: `buscarEventosNaJanela` cacheado (`cacheLife('minutes')`, tag por empresa). `updateTag` em `criarEvento`, `atualizarEvento` e `excluirEvento`.
- **Decisão de design (diverge do texto original do plano):** o `updateTag` foi colocado dentro do próprio método do service, logo após a escrita, em vez de nas `actions.ts` (que é onde `revalidatePath` já vive hoje). Motivo: a tag é definida no mesmo arquivo que a lê (`cacheTag`), então a invalidação correspondente fica ao lado, reduzindo o risco de esquecer de invalidar ou digitar uma tag diferente numa `actions.ts` distante. `revalidatePath` nas actions continua como estava, sem mudança.
- **Resolvido:** `role.service.ts` estendia `BaseService` (que resolve `empresaId` automaticamente via `getUsuarioAtualContexto()` → `getAccessContext()` → `cookies()`), impedindo `"use cache"` em `listarTodos`/`listarComContagemDeMembros`. Solução: os dois métodos passaram a receber `empresaId` explícito como parâmetro (igual ao padrão já usado em todo `empresaService`), em vez de resolvê-lo sozinhos por cookie — `BaseService` não foi alterado, e os métodos de escrita (`atualizar`/`remover`) continuam com o auto-scoping de sempre. As duas pages que chamavam esses métodos (`app/dashboard/empresa/membros/page.tsx`, `app/dashboard/empresa/papeis/page.tsx`) já tinham o `empresaId` disponível via `getAccessContext()`, então só precisaram passar o valor adiante. `criarPapel`, `atualizarPermissoes`, `renomear` e `removerPapel` agora chamam `updateTag(papeisTag(empresaId))`. `userService` não precisou de mudança (seus métodos usados em render não passam por `BaseService`), mas também não foi cacheado nesta fase.
- **Achado ao rodar a suíte de testes:** `tests/services/plano-matriz.test.ts` importa o `plano.service.ts` real (sem mock) e quebrou, porque `cacheLife()`/`cacheTag()` só funcionam dentro do runtime do Next com `cacheComponents` habilitado — fora dele (Vitest) essas funções lançam. Corrigido mockando `next/cache` nesse teste (`cacheLife`/`cacheTag` como no-op). Os demais testes que tocam os services alterados (`papeis.test.ts`, `empresas.test.ts`, `convite-membro-empresa.test.ts`, `agenda-empresa.test.ts`) já mockavam o service inteiro, então não foram afetados. **Atenção para daqui pra frente:** qualquer teste novo que exercite a implementação real (não mockada) de um service com `"use cache"` precisa mockar `next/cache` incluindo `cacheLife`/`cacheTag`/`updateTag`, senão quebra do mesmo jeito. `pnpm test` (82 testes) e `pnpm lint` seguem passando.
- [ ] Extrair a parte de banco de `getAccessContext()` (`db.user.findUnique` com memberships) para uma função interna cacheada, recebendo `userId` como argumento — fica para a Fase 2, junto da extração do gate de autenticação (fazem parte do mesmo componente).

## Fase 2 — Cache de `getAccessContext()` + gate de autenticação

- [x] `getAccessContext()` decomposto em 3 camadas cacheáveis independentes, cada uma invalidada pelo que realmente a afeta (evita ter que invalidar o cache de cada usuário quando só a permissão de um papel muda):
  - `buscarUsuarioComMembrosCached(usuarioId)` — vínculos de empresa do usuário, sem permissões do papel. Tag `user:${usuarioId}`.
  - `buscarPapelParaAccessContextCached(roleId, empresaId)` — nome/permissões do papel. Reusa `papeisTag(empresaId)` (já invalidado por `criarPapel`/`atualizarPermissoes`/`renomear`/`removerPapel`).
  - `planoService.buscarMatriz(planoId)` — já cacheado desde a Fase 1.
  - A leitura do cookie `empresa_ativa_id` continua fora de cache (é sempre lida fresca, só usada pra escolher qual membership da lista já cacheada é a "ativa").
- [x] `updateTag(userTag(usuarioId))` adicionado em todo lugar que muda o vínculo de um usuário específico: `empresaService.criarEmpresa`, `alterarPapelMembro`, `inativarMembro`, `aceitarConvite`, e `promoverAAdminAction` (`app/dashboard/_components/actions.ts`).
- [x] `tsc --noEmit`, `pnpm lint` e `pnpm test` (82 testes) passando.
- **Validado de ponta a ponta com login real:** rodado `pnpm db:seed` (idempotente, upsert) e testado via browser — login como `proprietario@example.com`, troca do papel de `financeiro@example.com` de Administrador para Secretário em `/dashboard/empresa/membros` (lista atualiza na hora, toast "Perfil atualizado"), depois login como `financeiro@example.com`: sidebar já mostra "Secretário" imediatamente, confirmando que `updateTag(userTag(...))` invalidou o cache de `getAccessContext()` do próprio usuário afetado, não só do administrador que fez a mutação. Revertido o papel de volta para Administrador ao final do teste, sem deixar dado de teste divergente do seed.

## Fase 2 (continuação) — decisão: não extrair o gate de autenticação

- **Decidido com o usuário: não fazer.** `components/sidebar/layout.tsx` e os layouts que fazem `getAccessContext()`/`auth()` (`dashboard`, `agenda`, `admin`, `empresa`, `docs`, `emails`) são 100% autenticados — não existe conteúdo público que viraria "shell estático" ali. Extrair isso para trás de `<Suspense>` exigiria criar skeletons de loading só para satisfazer a validação do Cache Components, sem ganho real de performance (a área é sempre dinâmica por natureza).
- **Mantido `instant = false` permanentemente** nessas rotas (não é um estado temporário a "arrumar depois" — o próprio Next trata isso como opção válida para rotas que nunca produziriam shell estático). O ganho de cache de dados (Fases 1 e 2 anteriores) já foi entregue independente disso.
- Rotas públicas/auth (`app/page.tsx`, já migrado na Fase 0) continuam candidatas a essa extração se algum dia ganharem mais conteúdo estático, mas isso não faz parte deste plano.

## Fase 3 — Convertida para as rotas públicas restantes; demais rotas ficam com `instant = false`

Já feito: `app/page.tsx` (Fase 0). Demais páginas públicas (`app/(auth)/login`, `app/(auth)/cadastro`, `app/fale-conosco`) e todas as rotas autenticadas permanecem com `instant = false` por decisão da Fase 2 acima — não há trabalho adicional de conversão de shell estático planejado.

## Fase 4 — Auditoria de invalidação nas Server Actions

- [x] Feito como parte das Fases 1 e 2: `updateTag` foi colocado direto nos services (`empresa.service.ts`, `plano.service.ts`, `agendamento.service.ts`, `role.service.ts`) e em `promoverAAdminAction`, ao invés de nas `actions.ts` — decisão registrada na Fase 1. `revalidatePath` das actions não foi alterado.
- [x] Nenhuma invalidação nova precisa rodar fora de Server Action (webhook/route handler) — todos os pontos de `updateTag` adicionados vivem em Server Actions ou em métodos de service chamados só a partir delas.

## Observação sobre escopo

Migração grande (~30 arquivos entre services, layouts, pages e actions) num app multi-tenant com permissões. Cada fase é independentemente testável e deve ser validada antes de avançar para a próxima.
